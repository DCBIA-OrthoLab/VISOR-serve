Le moteur parallele : VRAM, RAM et channels

Comment un run obtient de la memoire, qui decide quoi, et ou. Exemple deroule : AMASSS.

Ce document explique le chemin complet entre « un clinicien clique Apply » et « cinq modeles nnUNet tournent de front sur la carte ». Les chiffres cites sont ceux mesures sur la machine de developpement le 25 septembre 2026 ; ils changent avec la machine, la mecanique non.

1. Deux coupes, deux raisons

Le travail est divise deux fois, a deux endroits, pour deux raisons qui n'ont rien a voir. Les confondre est l'erreur qui rend tout le mecanisme inerte.

Le piege, vecu. Le plafond de la coupe 2 etait compte sur l'axe de la coupe 1 (scans). Sur le cas courant — un seul patient — cela donnait 1, et AMASSS demandait cinq structures pour s'en voir accorder une. La carte restait a 2,4 GiB et le run durait ce qu'il avait toujours dure.

2. Deux declarations allument le mecanisme

Rien de tout ceci ne s'applique a un tool qui ne le demande pas. Une capacite que personne n'a declaree n'est pas une capacite que le serveur peut supposer : ouvrir plusieurs channels dans une boucle qui partage un fichier temporaire corrompt ses propres sorties, en silence.

3. Le budget de la machine

Le serveur se dimensionne a la machine, en lisant la limite cgroup avant le noyau — les cpus: et memory: d'un conteneur sont donc honores et un pod Kubernetes ne demande aucun cas particulier.

# server/resources.py:292
share = SADT_RESOURCE_SHARE          # 0.75 par defaut
vram  = _budget_for(SADT_VRAM_BUDGET, vram_free, share)

Contre ce qui est LIBRE, pas contre ce que la carte contient. La part existe pour laisser de la place, et elle ne peut pas liberer une memoire qu'un autre process a deja prise.

4. Le cout d'un tool : une DROITE, pas un maximum

C'est le coeur du sujet. Un cout n'est pas un nombre, c'est fixe + marginal × largeur.

# server/execution/costs.py:404
def _predict(one, marginal, widths, channels):
    if widths >= 2:                           # l'ordonnee a ete MESUREE
        return one + marginal * (channels - 1)
    return max(one, marginal * channels)      # un seul point : le pire des deux

La partie fixe, c'est le contexte CUDA et le modele resident, que tout tool GPU paie une fois. Le marginal, c'est le plan de travail de chaque channel supplementaire. Mesure sur deux tools de formes opposees — un nnUNet 3D et un UNet 2D sur rendu multi-vues, rien en commun — les deux sont a environ trois quarts fixes.

Avec un seul point, on ne peut pas separer les deux

Un point admet deux lectures : le pic entier est admissible comme fixe, et il est admissible comme w channels de marginal. Avec un point il n'y a rien pour trancher, donc le modele prend la pire des deux reponses — plat en dessous de w, proportionnel au-dessus. Deviner l'une des deux est la facon dont une reservation devient trop petite, dans un sens ou dans l'autre.

6. Est-ce que ca tient ?

# server/execution/admission.py:295  --  _would_fit()
share = max(1, int(among))       # ce run PLUS tout ce qui attend derriere
if demand.cpus       * share + held_cpus > budget.cpus:       return False
if demand.ram_bytes  * share + held_ram  > budget.ram_bytes:  return False
if demand.vram_bytes * share + held_vram > budget.vram_bytes: return False

Deux passes, et l'ordre est la politique :

  • Equitable. Cette forme tiendrait-elle encore si chaque run deja en attente prenait la meme ? Une tete de file qui prend la forme la plus large qui passe laisse quarante runs derriere elle sans rien.
  • Gourmande. Si personne n'attend, la plus large qui tient.

L'echelle descend depuis le plafond : 5 → 4 → 3 → 2 → 1. La premiere qui passe est celle qui est reservee, et son nombre de channels est ecrit dans l'environnement du fils : SADT_CHANNELS et SADT_CHANNEL_BUDGET.

7. Le tool demande — en items, jamais en octets

# tools/AMASSS/src/sadt_amasss/pipeline.py
width = _channels_for(sup, len(models), num_workers)   # « j'ai 5 structures »

# server/execution/runner.py:2134  --  _Supervisor.channels()
room = _channel_budget()
if room is None:
    return _record_width(1)          # aucun serveur autour de ce run
answer = _channels_affordable(tool, room)
answer = min(answer, wanted, int(SADT_CHANNELS), SADT_MAX_CHANNELS)
return max(1, answer)

Le tool ne dit jamais un nombre d'octets. Il ne peut pas le savoir : cela depend du scan, des poids, de la version de torch. Il dit combien de choses il a a faire, et le serveur convertit avec ce que ce tool a coute aux runs precedents.

Et l'argent etait deja mis de cote a l'etape 5. sup.channels() ne fait que repartir une place deja obtenue — c'est ce qui rend sur de repondre aussi tard : rien ne peut etre sur-engage.

Le prix de ce marche, ecrit plutot que cache : un run qui n'ouvre qu'un channel garde sa part entiere toute sa vie. Demander cinq et n'en ouvrir qu'un immobilise la place des cinq.

Lu parle toolla table de couts
# tools/AMASSS/src/sadt_amasss/pipeline.py
progress.set_width(width)                    # autour de l'inference SEULEMENT
with futures.ThreadPoolExecutor(max_workers=width) as pool:
    ...                                      # 1 structure = 1 modele resident
progress.set_width(None)                     # les phases serielles ne declarent rien

Le serveur garde la largeur la plus etroite qu'on lui a dite, et divise le pic du run par elle. Un enregistrement sans largeur est ignore, pas lu comme 1 — c'est ce qui permet a un tool de declarer la largeur de la phase qui en a une, et de se taire pendant les phases serielles autour.

AMASSS lit sa cohorte en serie, predit ses structures de front, puis assemble en serie. Declarer la permission pendant les phases serielles mettrait une largeur elevee en vigueur la ou le pic se produit, et enseignerait un cout par channel trop bas : la direction qui finit en out-of-memory.

9. La boucle

Consequence pratique : le premier run large est sur-reserve, parce que la table n'a qu'une colonne de points et doit supposer le proportionnel. Apres lui, l'ajustement a deux largeurs et la reservation devient juste. C'est exactement ce que montre la fenetre d'AMASSS ci-dessus.

10. Deux pieges que les octets ne portent pas

Zero a deux sens opposes. Un tool mesure a vram = 0 ne coute rien a la carte et peut la partager avec n'importe quoi. Un tool dont toutes les lectures ont ete refusees — parce qu'elles venaient de runs contendus — ne sait rien, et reserver zero pour lui empilerait des runs sur une carte que le serveur croit vide. Les octets ne portent pas cette difference ; le drapeau vram_known si, et un tool inconnu tourne seul jusqu'a ce qu'une lecture soit crue.

Une lecture de carte venue d'un run contendu est refusee. Sur un pilote qui ne repond rien a --query-compute-apps, le seul chiffre disponible est la croissance de la carte entiere — ce qui compte l'allocation de chaque voisin comme si elle appartenait a ce run. Le refus est ecrit comme null, et la fenetre oublie par ressource pour que vingt refus ne chassent pas vingt mesures.
